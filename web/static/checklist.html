Agent Runtime 프로덕션 체크리스트

균형 잡힌 4대 범주(Runtime & State · Identity & Governance · Safety & Guardrails · Delivery, Eval & Observability)로 재구성하고, ① 선택한 환경 고유 항목과 ② 전 환경 공통 항목(COMMON-*)을 중복 없이 분리했습니다. Agent Runtime에 가까울수록 플랫폼 기본 제공이 많아 가볍고, Cloud Run·GKE로 갈수록 직접 챙겨야 할 런타임 항목이 늘어납니다. 모든 항목의 Check와 Best Practice에는 공식 문서 근거 링크가 함께 제공됩니다.

Best Practice
Agent Runtime에 기본으로 연결되는 VertexAiSessionService를 그대로 사용하고, 코드에서 다른 세션 서비스로 바꾸지 않습니다. (Agent Platform Sessions · ADK Sessions)

Agent Gateway (외부 호출 통제)

Check
에이전트가 무엇을 호출할지는 LLM이 실행 시점에 정하므로, 코드 리뷰나 단순 방화벽·ALB만으로는 외부 호출을 통제할 수 없습니다. Agent Gateway(AGENT_TO_ANYWHERE)가 Agent Identity · Agent Registry · IAP V2 정책(roles/iap.egressor CEL) · Model Armor 검사 · 컨테이너 TLS CA 신뢰까지 한 세트로 연결되어 있는지 확인합니다.
Best Practice
단순 게이트웨이 생성으로 끝나지 않습니다. ① Agent Identity(AR-ID1)·Agent Registry(AR-ID2)를 먼저 연결하고, ② AGENT_TO_ANYWHERE 게이트웨이에 AuthzExtension/AuthzPolicy(IAP V2, 반드시 DRY_RUN 시작 → 로그 검증 후 ENFORCED 전환해 HTTP 498 방지)와 MCP 도구별 roles/iap.egressor CEL 정책·Model Armor(piAndJailbreak·sdp) 검사를 부착하며, ③ service.tf의 agent_gateway_config 바인딩과 Dockerfile의 AGENT_GATEWAY_ROOT_CERTIFICATES CA 신뢰까지 함께 구성합니다. (외부 클라이언트 인바운드 보호 시 CLIENT_TO_AGENT + roles/iap.httpsResourceAccessor 별도 구성) (Agent Gateway · Model Armor)
AR-SF2조건부 · AI 생성 코드 실행

AI 생성 코드 격리 (Code Execution)

Check
AI가 만든 코드는 신뢰할 수 없어, Agent Runtime 컨테이너에서 그대로 실행하면 에이전트 신원·자격증명이 탈취될 수 있습니다. 이런 코드가 관리형 Code Execution 샌드박스에서 격리되어 실행되는지 확인합니다.
Best Practice
에이전트의 코드 실행을 Agent Platform Code Execution(관리형 샌드박스)에 맡깁니다. 샌드박스는 1초 이내에 생성되고 실행 상태를 TTL 동안 유지합니다. (Agent Platform Code Execution)

Check

Agent Gateway (외부 호출 통제)

Check

Best Practice
단순 리소스 생성으로 끝나지 않습니다. ① Agent Identity(CR-ID2)와 Agent Registry(CR-ID3)에 Cloud Run 에이전트·MCP 대상을 등록하고, ② PSC Network Attachment(private_ip_google_access=true) + Cloud DNS(*.run.app 등)로 Egress 경로를 연결하며, ③ AuthzExtension/AuthzPolicy(IAP V2 DRY_RUN→ENFORCED, roles/iap.egressor CEL)와 Model Armor 필터(piAndJailbreak·sdp)를 적용한 뒤 curl이 아닌 런타임 SDK(Python)로 정책 동작을 검증합니다. (Agent Gateway for Cloud Run · Model Armor)
CR-SF2조건부 · AI 생성 코드 실행Preview

AI 생성 코드 격리 (Cloud Run sandboxes)

Check
AI가 만든 코드는 신뢰할 수 없어, 에이전트 컨테이너에서 그대로 실행하면 서비스 계정 토큰이나 비밀값이 탈취될 수 있습니다. 이런 코드가 Cloud Run sandbox에서 격리되어 실행되는지 확인합니다.
Best Practice
서비스에 --sandbox-launcher(2세대 실행 환경)를 켜고, 에이전트의 코드 실행 도구가 Cloud Run sandbox에서 코드를 실행하게 합니다. 샌드박스는 비밀값·환경변수·메타데이터 서버에 접근할 수 없고 외부 네트워크도 기본 차단됩니다. (Code execution in Cloud Run)

Cloud Trace · 프롬프트 미기록

Check

GKE-RS3필수

무중단 종료 (긴 응답 보호)

Check
에이전트 한 턴은 LLM 스트리밍과 도구 호출로 수십 초 이상 걸려, 기본 종료 유예 시간(30초)으로는 배포·노드 업그레이드 때 응답이 잘릴 수 있습니다. terminationGracePeriodSeconds가 최대 응답 시간보다 길고, 종료 중에는 새 요청을 받지 않는지 확인합니다.
Best Practice
terminationGracePeriodSeconds를 최대 응답 시간 이상으로 두고, preStop과 readiness 프로브로 진행 중인 응답을 마친 뒤 종료합니다. (Pod termination · Kubernetes Probes)
GKE-RS4조건부 · 자주 일시정지·재개하는 상태 유지형 에이전트

에이전트 일시정지 · 복원 (Agent Substrate · Agent Sandbox)

Check
세션별 실행 환경을 갖는 상태 유지형 에이전트는 대부분의 시간을 입력이나 트리거를 기다리며 보내는데, 그동안 Pod가 CPU·메모리를 계속 점유합니다. 유휴 에이전트가 일시정지되어 컴퓨팅을 반납하고, 요청이 오면 메모리·작업 파일 상태가 복원되는지 확인합니다.
Best Practice
Agent Substrate on GKE에서 실행해 유휴 actor를 Cloud Storage 스냅샷으로 일시정지하고 워커의 CPU·메모리를 반납하며, 요청 시 1초 이내에 복원합니다(GKE Standard 1.37 이상, x86 노드). Agent Sandbox on GKE를 써야 하는 경우에는 Sandbox를 Suspended로 전환하기 전에 Pod snapshot(gVisor 전용, 복원 약 3~5초)으로 상태를 저장합니다. (Plan an architecture for AI agent workloads on GKE · Agent Substrate on GKE · Agent Sandbox on GKE)

Deployment에 에이전트 유형 레이블을 지정해 Agent Registry에 자동 등록합니다. (Agent Registry overview · About Agent Identity for GKE)

AI 생성 코드 격리 (Agent Substrate · Agent Sandbox)

Check
AI가 만든 코드는 신뢰할 수 없어, 에이전트 Pod 안에서 그대로 실행하면 자격증명 탈취나 노드 침해로 이어질 수 있습니다. 이런 코드가 에이전트 Pod가 아닌 격리된 샌드박스(Agent Substrate 또는 Agent Sandbox)에서 실행되는지 확인합니다.
Best Practice
AI 생성 코드는 에이전트 Pod가 아닌 격리된 샌드박스에서 실행합니다. Agent Substrate on GKE를 기본으로 사용하고(GKE Standard 1.37 이상, x86 노드), 상시 실행 에이전트, 사이드카 등 전체 PodSpec, Arm 노드, Autopilot이 필요하면 Agent Sandbox on GKE를 사용합니다. (Plan an architecture for AI agent workloads on GKE · Agent Substrate on GKE · Agent Sandbox on GKE)
GKE-SF2조건부 · MCP·외부 도구 호출Preview

Agent Gateway for GKE (외부 호출 통제)

Check
에이전트가 무엇을 호출할지는 LLM이 실행 시점에 정하므로, 일반 Ingress·Gateway만으로는 MCP·외부 도구 호출을 통제할 수 없습니다. Agent Gateway for GKE(Standard Pod 전용 · Rapid 1.37.2+ · Ambient · Dataplane V2 · Fleet · Proxy-only subnet)가 Ingress/Egress CRD 정책 및 Model Armor 바인딩과 함께 구성되어 있는지 확인합니다.
Best Practice
일반 Gateway 생성으로 끝나지 않습니다. Standard Pod 환경(Agent Sandbox·Substrate 미지원)에서 ① Ingress는 Gateway + HTTPRoute + GCPAgentGateway + GCPAuthzPolicy(L7 MCP tools/list·tools/call RBAC) + GCPExtensionBinding(Model Armor, 반드시 GCPAgentGateway 타겟)을 구성하고, ② Egress는 네임스페이스 networking.gke.io/dataplane-mode=ambient 라벨 + GCPBackend(SWP) + GCPEgressPolicy(클러스터 CIDR 제외) + 컨트롤 플레인 IAP/Model Armor ExtensionBinding을 함께 구성합니다. (Agent Gateway for GKE · Model Armor)
