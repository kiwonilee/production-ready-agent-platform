Agent Runtime 프로덕션 체크리스트

배포 환경마다 항목을 따로 묶었습니다. Agent Runtime에 가까울수록 Fully Managed라 플랫폼이 기본 제공하는 것이 많고, GKE에 가까울수록 직접 구성해야 하는 대신 제어권과 유연성이 큽니다. 일반적인 플랫폼 Best Practice가 아니라 에이전트의 특성(대화 상태, 긴 응답, 비결정적 출력, 자율적인 도구 호출) 때문에 필요한 항목만 정리했습니다. 각 항목의 Check는 왜 필요한지와 무엇을 확인하는지를, Best Practice는 어떻게 하는지를 설명합니다.

Features

에이전트 기능
AR-F1조건부 · 멀티턴 대화

관리형 영속 세션 저장 (VertexAiSessionService)

Check
Agent Runtime에는 VertexAiSessionService가 기본으로 연결되지만, 코드에서 InMemorySessionService로 덮어쓰면 재시작·스케일아웃 때 대화가 끊깁니다. 기본 관리형 세션을 그대로 쓰는지 확인합니다.
Best Practice
Agent Runtime에 기본으로 연결되는 VertexAiSessionService를 그대로 사용하고, 코드에서 다른 세션 서비스로 바꾸지 않습니다. (Agent Platform Sessions · ADK Sessions)
AR-F2조건부 · 장기 기억 필요

관리형 장기 기억 저장 (VertexAiMemoryBankService)

Check
개인화 에이전트는 세션이 끝난 뒤에도 사용자의 선호와 사실을 기억해야 합니다. 이런 에이전트에 Memory Bank가 연결되어 있는지 확인합니다.
Best Practice
VertexAiMemoryBankService(Memory Bank)로 세션 간 기억을 관리합니다. 같은 Agent Runtime 인스턴스의 Memory Bank를 사용합니다. (Memory Bank · ADK Memory)

Delivery & Eval

배포 · 품질 평가
AR-D1필수

CI/CD 파이프라인 (agents-cli)

Check
에이전트 변경은 배포 전에 자동으로 테스트·평가되어야 하는데, 사람이 직접 배포하면 이 검증을 건너뛰게 됩니다. agents-cli로 생성한 CI/CD 파이프라인(.cloudbuild/)이 있는지 확인합니다.
Best Practice
agents-cli scaffold enhance . --cicd-runner google_cloud_build로 파이프라인(.cloudbuild/)을 생성해 PR 테스트 → staging 배포 → prod 승인 흐름을 코드로 둡니다. CI/CD 인프라 생성(agents-cli infra cicd)은 운영 환경 구성이므로 직접 수행합니다. (agents-cli CI/CD)
AR-D2필수

평가 데이터셋 · 평가 게이트

Check
LLM 출력은 비결정적이라 프롬프트·모델·도구를 바꾸면 단위 테스트로 잡히지 않는 품질 저하가 생깁니다. 평가 데이터셋이 있고, 파이프라인 staging 단계에서 평가 점수가 기준에 못 미치면 prod 배포로 넘어가지 않는지 확인합니다.
Best Practice
agents-cli eval용 평가 데이터셋을 두고, 파이프라인 staging 단계에서 agents-cli eval run 점수를 기준값과 비교해 미달이면 실패하게 합니다(eval run은 점수와 무관하게 성공으로 끝나므로 비교 단계가 필요). (ADK Evaluate)

AR-OB1필수

프롬프트 미기록

Check
트레이스는 플랫폼이 기본으로 수집하지만, 프롬프트·응답에는 사용자 개인정보가 섞입니다. 트레이스에 메시지 본문이 기록되지 않는지 확인합니다.
Best Practice
GenAI 메시지 본문 수집은 끈 상태로 둡니다. (OpenTelemetry GenAI)

Security

보안
AR-S1필수

에이전트 전용 신원 · 최소 권한

Check
에이전트는 스스로 판단해 도구·API를 호출하므로, 권한이 넓으면 프롬프트 인젝션 한 번으로도 피해가 커집니다. 기본 서비스 에이전트 권한에 의존하지 않고 에이전트 전용 신원으로 실행되고 필요한 권한만 갖는지 확인합니다.
Best Practice
Agent Identity(Preview)로 에이전트 고유 신원을 부여하고, 사용할 수 없으면 전용 서비스 계정을 지정합니다. 어느 쪽이든 필요한 최소 역할만 부여합니다. (Agent Identity · IAM 보안 가이드)
AR-S2필수Preview

Agent Registry 등록

Check
팀마다 에이전트·MCP 서버를 만들면 조직은 어떤 에이전트가 무엇을 호출하는지 파악하기 어려워집니다. 에이전트가 Agent Registry에 등록되어 있는지 확인합니다.
Best Practice
Agent Registry에 에이전트를 등록해 조직 단위로 가시성과 거버넌스를 확보합니다. (참고 링크 확인 중)
AR-S3조건부 · MCP·외부 도구 호출Preview

Agent Gateway (외부 호출 통제)

Check
에이전트가 무엇을 호출할지는 LLM이 실행 시점에 정하므로, 코드 리뷰만으로는 외부 호출을 통제할 수 없습니다. MCP·외부 도구 호출이 Agent Gateway를 거쳐 정책으로 통제되는지 확인합니다.
Best Practice
Agent Gateway를 연결해 에이전트의 외부 호출에 접근 정책을 적용하고, 정책은 시험 모드로 검증한 뒤 강제 모드로 전환합니다. (Agent Gateway)
AR-S4조건부 · AI 생성 코드 실행

AI 생성 코드 격리 (Code Execution)

Check
AI가 만든 코드는 신뢰할 수 없어, Agent Runtime 컨테이너에서 그대로 실행하면 에이전트 신원·자격증명이 탈취될 수 있습니다. 이런 코드가 관리형 Code Execution 샌드박스에서 격리되어 실행되는지 확인합니다.
Best Practice
에이전트의 코드 실행을 Agent Platform Code Execution(관리형 샌드박스)에 맡깁니다. 샌드박스는 1초 이내에 생성되고 실행 상태를 TTL 동안 유지합니다. (Agent Platform Code Execution)
AR-S5조건부 · 사용자 대신 외부 도구 호출Preview

사용자 위임 인증 (Agent Identity auth manager)

Check
에이전트는 사용자를 대신해 Jira·GitHub 같은 외부 시스템을 호출하는데, 정적 API 키나 개인 토큰을 쓰면 모든 사용자가 같은 권한으로 접근하고 키가 유출되면 피해가 큽니다. 사용자 대신 호출하는 외부 도구가 auth manager로 위임받은 사용자 OAuth 토큰을 쓰는지 확인합니다.
Best Practice
auth manager에 auth provider(3-legged OAuth)를 구성하고, ADK가 도구·MCP 호출 시 사용자 위임 토큰을 받아 인증 헤더를 붙이게 합니다. 정적 API 키·PAT는 코드와 환경변수에 두지 않습니다. (Agent Identity auth manager · 3-legged OAuth with auth manager)

Features

에이전트 기능
CR-F1조건부 · 멀티턴 대화

관리형 영속 세션 저장 (VertexAiSessionService)

Check

Best Practice
VertexAiSessionService로 세션을 저장해 인스턴스 재시작·스케일아웃 후에도 대화를 이어갑니다. Agent Platform 인스턴스 ID로 세션 저장소에 연결합니다. (ADK Sessions · Agent Platform Sessions)

Best Practice

CR-OB1필수

Cloud Trace · 프롬프트 미기록

Check
에이전트는 한 요청 안에서 추론과 도구 호출을 여러 번 반복하므로, 단계별 트레이스가 있어야 실패·지연 원인을 찾을 수 있습니다. 에이전트·도구 호출이 Cloud Trace에 수집되고, 개인정보가 섞인 프롬프트·응답 본문은 기록되지 않는지 확인합니다.

보안
CR-S1필수

인증된 호출만 허용

Check
에이전트는 호출될 때마다 토큰 비용이 들고, 공개된 엔드포인트는 그대로 프롬프트 인젝션의 공격 대상이 됩니다. 서비스에 allUsers 호출 권한이 없어 인증된 호출만 받는지 확인합니다.
Best Practice
Cloud Run IAM 인증을 요구하고, 프런트엔드나 다른 서비스는 전용 서비스 계정으로 호출합니다. (Cloud Run 인증)
CR-S2필수

에이전트 전용 신원 · 최소 권한

Check

Best Practice
Agent Identity(Preview)로 에이전트 고유 신원을 부여하고, 사용할 수 없으면 전용 서비스 계정을 씁니다. 어느 쪽이든 필요한 최소 역할만 부여합니다. (Agent Identity · Cloud Run service identity · IAM 보안 가이드)

Best Practice
서비스를 에이전트(또는 MCP 서버) 유형으로 배포해 Agent Registry에 자동 등록합니다. (Cloud Run Agent Platform 기능)

Best Practice
Agent Gateway for Cloud Run으로 에이전트의 외부 호출에 접근 정책을 적용합니다. (Agent Gateway for Cloud Run)
CR-S5조건부 · AI 생성 코드 실행Preview

AI 생성 코드 격리 (Cloud Run sandboxes)

Check
AI가 만든 코드는 신뢰할 수 없어, 에이전트 컨테이너에서 그대로 실행하면 서비스 계정 토큰이나 비밀값이 탈취될 수 있습니다. 이런 코드가 Cloud Run sandbox에서 격리되어 실행되는지 확인합니다.
Best Practice
서비스에 --sandbox-launcher(2세대 실행 환경)를 켜고, 에이전트의 코드 실행 도구가 Cloud Run sandbox에서 코드를 실행하게 합니다. 샌드박스는 비밀값·환경변수·메타데이터 서버에 접근할 수 없고 외부 네트워크도 기본 차단됩니다. (Code execution in Cloud Run)

Optimize

런타임 최적화
GKE-O1필수

무중단 종료 (긴 응답 보호)

Check
에이전트 한 턴은 LLM 스트리밍과 도구 호출로 수십 초 이상 걸려, 기본 종료 유예 시간(30초)으로는 배포·노드 업그레이드 때 응답이 잘릴 수 있습니다. terminationGracePeriodSeconds가 최대 응답 시간보다 길고, 종료 중에는 새 요청을 받지 않는지 확인합니다.
Best Practice
terminationGracePeriodSeconds를 최대 응답 시간 이상으로 두고, preStop과 readiness 프로브로 진행 중인 응답을 마친 뒤 종료합니다. (Pod termination · Kubernetes Probes)
GKE-O2조건부 · 자주 일시정지·재개하는 상태 유지형 에이전트

에이전트 일시정지 · 복원 (Agent Substrate · Agent Sandbox)

Check
세션별 실행 환경을 갖는 상태 유지형 에이전트는 대부분의 시간을 입력이나 트리거를 기다리며 보내는데, 그동안 Pod가 CPU·메모리를 계속 점유합니다. 유휴 에이전트가 일시정지되어 컴퓨팅을 반납하고, 요청이 오면 메모리·작업 파일 상태가 복원되는지 확인합니다.
Best Practice
Agent Substrate on GKE에서 실행해 유휴 actor를 Cloud Storage 스냅샷으로 일시정지하고 워커의 CPU·메모리를 반납하며, 요청 시 1초 이내에 복원합니다(GKE Standard 1.37 이상, x86 노드). Agent Sandbox on GKE를 써야 하는 경우에는 Sandbox를 Suspended로 전환하기 전에 Pod snapshot(gVisor 전용, 복원 약 3~5초)으로 상태를 저장합니다. (Plan an architecture for AI agent workloads on GKE · Agent Substrate on GKE · Agent Sandbox on GKE)

Delivery & Eval

배포 · 품질 평가
GKE-D1필수

CI/CD 파이프라인 (agents-cli)

Check
에이전트 변경은 배포 전에 자동으로 테스트·평가되어야 하는데, 사람이 직접 배포하면 이 검증을 건너뛰게 됩니다. agents-cli로 생성한 CI/CD 파이프라인(.cloudbuild/)이 있는지 확인합니다.
Best Practice
agents-cli scaffold enhance . --cicd-runner google_cloud_build로 파이프라인(.cloudbuild/)을 생성해 PR 테스트 → staging 배포 → prod 승인 흐름을 코드로 둡니다. CI/CD 인프라 생성(agents-cli infra cicd)은 운영 환경 구성이므로 직접 수행합니다. (agents-cli CI/CD)
GKE-D2필수

평가 데이터셋 · 평가 게이트

Check
LLM 출력은 비결정적이라 프롬프트·모델·도구를 바꾸면 단위 테스트로 잡히지 않는 품질 저하가 생깁니다. 평가 데이터셋이 있고, 파이프라인 staging 단계에서 평가 점수가 기준에 못 미치면 prod 배포로 넘어가지 않는지 확인합니다.
Best Practice
agents-cli eval용 평가 데이터셋을 두고, 파이프라인 staging 단계에서 agents-cli eval run 점수를 기준값과 비교해 미달이면 실패하게 합니다(eval run은 점수와 무관하게 성공으로 끝나므로 비교 단계가 필요). (ADK Evaluate)

Cloud Trace · 프롬프트 미기록

Check
에이전트는 한 요청 안에서 추론과 도구 호출을 여러 번 반복하므로, 단계별 트레이스가 있어야 실패·지연 원인을 찾을 수 있습니다. 에이전트·도구 호출이 Cloud Trace에 수집되고, 개인정보가 섞인 프롬프트·응답 본문은 기록되지 않는지 확인합니다.

GKE-S1필수

에이전트 전용 신원 · 최소 권한

Check
에이전트는 스스로 판단해 도구·API를 호출하므로, 권한이 넓으면 프롬프트 인젝션 한 번으로도 피해가 커집니다. Pod가 노드 기본 서비스 계정이 아닌 에이전트 전용 신원으로 실행되고 필요한 권한만 갖는지 확인합니다.
Best Practice
Agent Identity(Preview)로 에이전트 고유 신원을 부여하고, 사용할 수 없으면 Workload Identity로 전용 서비스 계정을 연결합니다. 어느 쪽이든 필요한 최소 역할만 부여합니다. (Agent Identity · Workload Identity · IAM 보안 가이드)
GKE-S2조건부 · AI 생성 코드 실행

AI 생성 코드 격리 (Agent Substrate · Agent Sandbox)

Check
AI가 만든 코드는 신뢰할 수 없어, 에이전트 Pod 안에서 그대로 실행하면 자격증명 탈취나 노드 침해로 이어질 수 있습니다. 이런 코드가 에이전트 Pod가 아닌 격리된 샌드박스(Agent Substrate 또는 Agent Sandbox)에서 실행되는지 확인합니다.
Best Practice
AI 생성 코드는 에이전트 Pod가 아닌 격리된 샌드박스에서 실행합니다. Agent Substrate on GKE를 기본으로 사용하고(GKE Standard 1.37 이상, x86 노드), 상시 실행 에이전트, 사이드카 등 전체 PodSpec, Arm 노드, Autopilot이 필요하면 Agent Sandbox on GKE를 사용합니다. (Plan an architecture for AI agent workloads on GKE · Agent Substrate on GKE · Agent Sandbox on GKE)

GKE-S4조건부 · MCP·외부 도구 호출Preview

Agent Gateway for GKE (외부 호출 통제)

Check
에이전트가 무엇을 호출할지는 LLM이 실행 시점에 정하므로, 코드 리뷰만으로는 외부 호출을 통제할 수 없습니다. MCP·외부 도구 호출이 Agent Gateway를 거쳐 정책으로 통제되는지 확인합니다.
Best Practice
Agent Gateway for GKE로 에이전트의 외부 호출에 접근 정책을 적용합니다. (Agent Gateway)
GKE-S5조건부 · 사용자 대신 외부 도구 호출Preview

사용자 위임 인증 (Agent Identity auth manager)

Check
에이전트는 사용자를 대신해 Jira·GitHub 같은 외부 시스템을 호출하는데, 정적 API 키나 개인 토큰을 쓰면 모든 사용자가 같은 권한으로 접근하고 키가 유출되면 피해가 큽니다. 사용자 대신 호출하는 외부 도구가 auth manager로 위임받은 사용자 OAuth 토큰을 쓰는지 확인합니다.
Best Practice
auth manager에 auth provider(3-legged OAuth)를 구성하고, ADK가 도구·MCP 호출 시 사용자 위임 토큰을 받아 인증 헤더를 붙이게 합니다. 정적 API 키·PAT는 코드와 환경변수에 두지 않습니다. (Agent Identity auth manager · 3-legged OAuth with auth manager)
