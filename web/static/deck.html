02
왜 Production-Readiness가 필요한가? Why AI Agents Break Standard Web Ops
로컬 데모의 성공은 상용 운영의 20%에 불과 — AI Agent 고유 실행 특성이 기존 운영 기준을 무너뜨림
AI 에이전트가 기존 웹 API와 다른 4가지 이유
전통적 Stateless REST API 가정이 깨지는 지점
TRAIT 01 · LONG-RUNNING
초장기 스트리밍 & 다중 도구 호출
1회 요청이 30~180초간 ReAct 루프·SSE 스트림을 유지 → 롤링 업데이트·기본 타임아웃 시 대화 즉각 끊김
TRAIT 02 · STATEFUL
멀티턴 상태 & 아티팩트 의존
인메모리 세션으로 배포하면 컨테이너 2개 스케일아웃·재시작 순간 직전 맥락과 생성 파일이 통째로 증발
TRAIT 03 · NON-DETERMINISTIC
비결정적 품질 회귀 (Eval 부재)
프롬프트 한 줄 수정해도 단위 테스트는 통과하지만 환각·도구 오호출 급증 → CI/CD 내 자동 평가 게이트 필수
TRAIT 04 · AUTONOMOUS RISK
자율 도구 실행 & PII 노출 위험
외부 API·코드 실행 권한이 과도하거나 트레이스 스팬에 고객 프롬프트 원문이 평문 적재되면 대형 보안 사고로 직결
현장 통증 — 개발팀은 ADK 로직에 집중하고 싶지만, 보안·네트워크·관측성·CI/CD 평가 설정은 런타임(Agent Runtime · Cloud Run · GKE)마다 완전히 달라 상용 전환에 수 주가 지연됨
본 플랫폼이 해결하는 미션 & 핵심 지표
표준화 · 자동화 · 무침습(Zero Over-Reach) 설계

환경별 Agent 특화 기능 ① — Agent Runtime & Cloud Run Managed vs. Serverless
에이전트 전용 관리형(Agent Runtime) vs. 유연한 서버리스 컨테이너(Cloud Run)
🛡️ Agent Runtime — 에이전트 전용 특화 기능
AI 에이전트를 위해 플랫폼에 기본 내장된 역량
  • Sub-second 초고속 응답 — Always-on 기반 관리형 워커로 콜드스타트 지연을 1초 미만으로 최소화
  • Managed Sessions & Memory Bank 내장 — DB 구축·운영 없이 VertexAiSessionService 멀티턴 영속 세션 및 장기 기억(365일) 기본 제공
  • Built-in OpenTelemetry & ADK Auth — ENABLE_TELEMETRY 기반 Cloud Trace 파이프라인 및 ADK 도구 인증 기본 통합
  • 네이티브 아웃바운드 Agent Gateway (AR-S3) — google_network_services_agent_gateway(AGENT_TO_ANYWHERE) + UAP V2 정책(DRY_RUN→ENFORCED)으로 에이전트 외부 호출 중앙 통제
  • 전용 SPIFFE Agent Identity & Registry — spec.identity_type="AGENT_IDENTITY"로 에이전트 고유 신원(AR-S1) · Agent Registry 등록(AR-S2)

⚡ Cloud Run — 서버리스 에이전트 특화 기능
컨테이너 자유도와 비용 효율을 극대화하는 역량
  • Scale-to-Zero & Pay-per-Use — 트래픽이 없을 때 인스턴스 0으로 축소되어 유휴 비용 제로(불규칙·버스트 워크로드 최적)
  • Agent Gateway for Cloud Run (CR-S4 · Preview) — MCP·외부 도구 호출에 접근 정책을 적용해 에이전트의 외부 호출을 중앙 통제
  • Agent / MCP 서버 자동 분기 등록 (CR-S3) — 일반 에이전트는 FUNCTIONAL_TYPE_AGENT + SPIFFE, FastMCP 서버는 FUNCTIONAL_TYPE_MCP_SERVER + 전용 SA로 Agent Registry 자동 등록

GKE는 일반 서빙을 넘어 Gateway · 비신뢰 코드 격리 · 초고밀도 · 자체 GPU/TPU 추론까지 지원

Standard GKE Pods
+ Agent Gateway for GKE

일반 멀티턴·도구 호출 ADK 에이전트 표준

  • Egress 중앙 통제 — Ambient 메시 + GCPBackend + GCPEgressPolicy → Secure Web Proxy(SWP) 연동

Agent Substrate on GKE

  • 10× 고밀도 · <500ms 복원 — 유휴 에이전트의 RAM+디스크 상태 전체를 GCS/Filestore에 스냅샷 후 0.5초 미만 재개
  • 전용 컨트롤 플레인 — ate.dev/v1alpha1 WorkerPool CRD + kubectl ate ActorTemplate
  • 내장 Egress Gateway — suspend 시 열린 소켓 제약 대응 + Zero-Metadata DPv2 NetworkPolicy

Agent 배포 관점 환경별 장단점 종합 Pros & Cons Analysis
3대 런타임의 강점과 트레이드오프를 명확히 이해해야 운영 실패와 과잉 설계를 방지
🛡️ Agent Runtime
장점 (Pros)
  • 가장 낮은 운영 부담 — 헬스체크·관리형 세션·OTel 수집을 플랫폼이 기본 제공
  • 1초 미만 응답성 — 대화형 UX에서 콜드스타트 체감 지연 최소화
  • 네이티브 Agent Gateway — UAP V2 기반 아웃바운드 거버넌스 즉시 결합
  • 장기 멀티턴·메모리 최적 — Memory Bank와 가장 매끄러운 통합
단점 · 고려사항 (Cons)
  • Always-on 과금 — 간헐적 트래픽에서도 유휴 인스턴스 비용 발생
  • 인프라 제어 한계 — 커스텀 네트워크 토폴로지·사이드카·컨테이너 OS 제어 제한
  • 사내망 구성 복잡도 — PSC Network Attachment(/28 PGA 서브넷) 사전 설계 필요
한 줄 평가 — DevOps 인력이 적고 장기 대화·메모리 중심 에이전트를 가장 빠르게 상용화할 때 최적
⚡ Cloud Run
장점 (Pros)
  • Scale-to-Zero 압도적 비용 효율 — 트래픽 없을 때 과금 0원, 예측 가능한 종량제
  • 컨테이너 · MCP 서버 최적 — 사이드카·커스텀 바이너리 자유 구성 및 MCP 자동 분기
  • 간편한 사내망 연동 — Direct VPC Egress로 기존 서브넷에 저지연 직접 연결
  • 검증된 GA 보안 스택 — Gen2 + IAP + SWP + Cloud Armor로 빠른 엔터프라이즈 인가
단점 · 고려사항 (Cons)
  • 세션 외부 연동 필수 — 기본 인메모리 휘발성이므로 Managed Session/DB 구성 필요
  • 콜드스타트 관리 — 0→1 기동 지연(startup_cpu_boost 또는 min_instances 보완)
  • Agent Gateway는 Preview — Agent Gateway for Cloud Run 정식 출시 전까지는 DRY_RUN으로 정책을 검증하며 도입
한 줄 평가 — 비용 최적화 · 경량/Stateless 에이전트 · MCP 도구 서버 호스팅의 표준 선택지
☸️ GKE
장점 (Pros)
  • 최강의 아키텍처 자유도 — Agent Gateway for GKE · Sandbox · Substrate 3대 특화 패턴
  • AI 생성 코드 격리 & 고밀도 — Agent Substrate 샌드박스(대안: Agent Sandbox) 및 0.5초 미만 RAM 스냅샷 복원
  • 자체 GPU/TPU 모델 통합 — Inference Gateway로 오픈 모델과 에이전트 동일 VPC 서빙
  • 기존 K8s 표준 흡수 — 사내 GitOps · 서비스 메시 · 멀티테넌시 거버넌스 그대로 적용
단점 · 고려사항 (Cons)
  • 운영·학습 곡선 가장 높음 — 멀티존·PDB·HPA·PSS·NetworkPolicy 같은 플랫폼 운영과 클러스터 수명 관리 (플랫폼 Skill 참고)
  • 초기 프로비저닝 시간 — 클러스터·서브넷·CRD 준비에 15~20분 이상 소요
  • 버전/모드 제약 관리 — AGW(Rapid ≥ 1.37.2), Substrate(Standard ≥ 1.37 전용) 조건 준수
한 줄 평가 — 대규모 엔터프라이즈 표준 · 코드 실행 샌드박스 · 자체 GPU LLM 환경의 최종 플랫폼

런타임 선택 Decision Framework
어떤 워크로드에 어떤 환경을 선택할 것인가?
Agent RuntimeMANAGED FIRST
장기 멀티턴 대화 · 개인화 기억(Memory Bank)이 핵심이고, 세션 DB·인프라 운영을 최소화하며 1초 미만 응답과 네이티브 Agent Gateway가 필요할 때
Cloud RunSERVERLESS FLEX
불규칙 트래픽(Scale-to-Zero) 비용 절감이 최우선이거나, 커스텀 컨테이너 · 사이드카 · FastMCP 도구 서버 및 빠른 HTTPS 상용 배포가 필요할 때
GKEK8S ENTERPRISE
기존 GKE 표준·VPC 거버넌스 통합, 비신뢰 코드 격리(Agent Sandbox), 수천 개 고밀도 에이전트(Substrate), 또는 자체 GPU/TPU 오픈 모델을 함께 운영할 때
하이브리드 권장 패턴 — 에이전트 본체는 Agent Runtime 또는 GKE에, 독립 도구 MCP 서버는 Cloud Run(FUNCTIONAL_TYPE_MCP_SERVER)에 배치하고 Agent Registry로 연결
지금 바로 시작하는 4단계 도입 로드맵
통합 웹 포털 & Antigravity Skill 실행 순서
1
체크리스트 & 조건 확정/checklist에서 타겟 런타임(CR·AR·GKE)과 조건(멀티턴 · 장기 기억 · AI 생성 코드 · 외부 도구) 확정
2
Antigravity Skill 1줄 설치 & 정적 스캔로컬 ADK / agents-cli 프로젝트에서 에이전트 특성 항목 갭 진단 및 Diff 미리보기 · 플랫폼 BP는 플랫폼 Skill 병행
3
인플레이스 자동 패치 & Eval Gate 배포/lab Step 0~7 따라 Terraform + agents-cli deploy + Staging agent-eval-gate 연동
