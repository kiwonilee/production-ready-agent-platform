A1
Feature Deep Dive ① · Agent Identity & auth manager SPIFFE ID & User-Delegated OAuth
에이전트 전용 암호화 신원(SPIFFE ID)과 사용자 위임 인증(3-legged OAuth)으로 공유 SA·정적 API 키 제거
왜 필요한가? · 2가지 인증 축
기존 공유 Service Account & 정적 PAT의 한계
  • 권한 과다 & 감사 추적 불가 — 여러 에이전트가 하나의 SA를 공유하면 프롬프트 인젝션 시 영향 범위가 프로젝트 전체로 확산
  • 정적 API 키 / PAT 유출 위험 — Jira·GitHub 등 외부 도구를 에이전트 공용 키로 호출하면 호출한 최종 사용자 권한 검증 불가
Agent Identity의 2대 보안 계층
1
에이전트 자체 신원 (Agent Identity · SPIFFE ID)조직 단위 워크로드 풀(agents.global.org-<ORG_ID>.system.id.goog/...)에서 에이전트별 독립 암호화 신원 발급 · 최소 권한 IAM 바인딩
2
사용자 위임 인증 (auth manager · 3-legged OAuth)Preview사용자 계정으로 외부 시스템 호출 시 정적 토큰 대신 GcpAuthProvider + google-adk[agent-identity]로 사용자별 OAuth 토큰 위임 발급
체크리스트 매핑 — 전용 신원(AR-S1 · CR-S2 · GKE-S1)은 필수, 사용자 위임 인증(AR-S5 · CR-S6 · GKE-S5)은 조건부·안내 전용

A2
Feature Deep Dive ② · Agent Registry Central Discovery & Governance Catalog · Preview
조직 내 모든 에이전트와 MCP 서버를 중앙 카탈로그에 자동 등록하고 하드코딩 URL 없는 동적 탐색 구현
핵심 역할 · 하이브리드 아키텍처 허브
왜 Agent Registry가 필요한가?
  • Shadow AI 방지 & 중앙 가시성 — Cloud Run · Agent Runtime · GKE에 흩어진 에이전트와 MCP 도구 서버를 단일 카탈로그(agentregistry.googleapis.com)로 통합 관리
  • 하드코딩 URL 제거 (Lazy Discovery) — 엔드포인트 URL을 코드에 박지 않고 레지스트리 이름으로 런타임에 안전하게 조회
  • Agent Gateway · App Hub 연계 기반 — 등록된 에이전트·MCP 자산에 거버넌스 정책과 호출 허용 목록을 일관되게 적용
3대 런타임 자동 등록 방식 (AR-S2 · CR-S3 · GKE-S3)
환경자동 등록 선언
Agent Runtimeidentity_type = "AGENT_IDENTITY" 배포 시 자동 등록
Cloud Runfunctional_type = "FUNCTIONAL_TYPE_AGENT" 또는 FastMCP 감지 시 "FUNCTIONAL_TYPE_MCP_SERVER" 자동 분기
GKEDeployment 라벨 registry.gke.io/functional-type: AGENT
ADK Lazy Discovery 전환 & 운영 검증
하드코딩 URL → AgentRegistry 동적 조회 전환
# ❌ 안티패턴: 환경별 URL 하드코딩 (스캐너 AMBER 탐지) mcp = McpToolset(url="https://currency-mcp-uc.a.run.app/mcp") # ✅ 권장: AgentRegistry 기반 Lazy Discovery from google.adk.integrations.agent_registry import AgentRegistry registry = AgentRegistry(project_id=PROJECT, location="us-central1") mcp = registry.get_mcp_toolset( mcp_server_name=os.environ["CURRENCY_MCP_REGISTRY_NAME"] ) a2a = registry.get_remote_a2a_agent( agent_name=os.environ["BILLING_AGENT_REGISTRY_NAME"] )

TRAIT 01 · LONG-RUNNING

TRAIT 04 · AUTONOMOUS RISK
자율 도구 실행 & PII 노출 위험
외부 API·코드 실행 권한이 과도하거나 트레이스 스팬에 고객 프롬프트 원문이 평문 적재되면 대형 보안 사고로 직결

환경별 Agent 특화 기능 ① — Agent Runtime & Cloud Run Managed vs. Serverless
에이전트 전용 관리형(Agent Runtime) vs. 유연한 서버리스 컨테이너(Cloud Run)
Agent Runtime — 에이전트 전용 특화 기능
AI 에이전트를 위해 플랫폼에 기본 내장된 역량
  • 낮은 콜드스타트 지연 — Always-on 기반 관리형 워커로 대화형 요청 대기 최소화
  • Managed Sessions & Memory Bank 내장 — DB 구축·운영 없이 VertexAiSessionService 멀티턴 영속 세션 및 장기 기억(Memory Bank) 기본 제공
  • Built-in OpenTelemetry & 관리형 Code Execution (AR-S4) — 기본 OTel 파이프라인 + AI 생성 코드를 1초 이내 생성되는 관리형 샌드박스에서 격리 실행
  • 네이티브 아웃바운드 Agent Gateway (AR-S3) — google_network_services_agent_gateway(AGENT_TO_ANYWHERE) + UAP V2 정책(DRY_RUN→ENFORCED)으로 에이전트 외부 호출 중앙 통제
  • 전용 SPIFFE Agent Identity · Registry · 위임 인증 — spec.identity_type="AGENT_IDENTITY"(AR-S1) · Agent Registry 등록(AR-S2) · auth manager(3LO, AR-S5)
ReasoningEngineManaged SessionsMemory BankCode ExecutionAGENT_TO_ANYWHERE AGW
Cloud Run — 서버리스 에이전트 특화 기능
컨테이너 자유도와 비용 효율을 극대화하는 역량
  • Scale-to-Zero & Pay-per-Use — 트래픽이 없을 때 인스턴스 0으로 축소되어 유휴 비용 제로(불규칙·버스트 워크로드 최적)
  • Agent Gateway for Cloud Run (CR-S4 · Preview) — MCP·외부 도구 호출에 접근 정책을 적용해 에이전트의 외부 호출을 중앙 통제
  • AI 생성 코드 격리 · Cloud Run sandboxes (CR-S5 · Preview) — --sandbox-launcher(2세대)로 비밀값·메타데이터·외부망이 차단된 샌드박스에서 AI 코드 실행
  • Agent / MCP 서버 자동 분기 등록 (CR-S3) — 일반 에이전트는 FUNCTIONAL_TYPE_AGENT + SPIFFE, FastMCP 서버는 FUNCTIONAL_TYPE_MCP_SERVER + 전용 SA로 Agent Registry 자동 등록
  • 커스텀 컨테이너 · Direct VPC Egress · Worker/Job — 사내 바이너리·사이드카·저지연 직접 VPC 연동 및 비동기 워커까지 단일 플랫폼 수용

A14
Agent 배포 관점 환경별 장단점 종합 Pros & Cons Analysis
3대 런타임의 강점과 트레이드오프를 명확히 이해해야 운영 실패와 과잉 설계를 방지
Agent Runtime
장점 (Pros)
  • 가장 낮은 운영 부담 — 헬스체크·관리형 세션·OTel 수집을 플랫폼이 기본 제공
  • 낮은 콜드스타트 지연 — 상시 대기 관리형 워커로 대화형 UX 체감 지연 최소화
  • 네이티브 Agent Gateway — UAP V2 기반 아웃바운드 거버넌스 즉시 결합
  • 장기 멀티턴·메모리 최적 — Memory Bank와 가장 매끄러운 통합
단점 · 고려사항 (Cons)
  • Always-on 과금 — 간헐적 트래픽에서도 유휴 인스턴스 비용 발생
  • 인프라 제어 한계 — 커스텀 네트워크 토폴로지·사이드카·컨테이너 OS 제어 제한
  • 사내망 구성 복잡도 — PSC Network Attachment(/28 PGA 서브넷) 사전 설계 필요
한 줄 평가 — DevOps 인력이 적고 장기 대화·메모리 중심 에이전트를 가장 빠르게 상용화할 때 최적
Cloud Run
장점 (Pros)
  • Scale-to-Zero 압도적 비용 효율 — 트래픽 없을 때 과금 0원, 예측 가능한 종량제
  • 컨테이너 · MCP 서버 최적 — 사이드카·커스텀 바이너리 자유 구성 및 MCP 자동 분기
  • 간편한 사내망 연동 — Direct VPC Egress로 기존 서브넷에 저지연 직접 연결
  • 검증된 GA 보안 스택 — Gen2 + IAP + SWP + Cloud Armor로 빠른 엔터프라이즈 인가
단점 · 고려사항 (Cons)
  • 세션 외부 연동 필수 — 기본 인메모리 휘발성이므로 Managed Session/DB 구성 필요
  • 콜드스타트 관리 — 0→1 기동 지연(startup_cpu_boost 또는 min_instances 보완)
  • Agent Gateway는 Preview — Agent Gateway for Cloud Run 정식 출시 전까지는 DRY_RUN으로 정책을 검증하며 도입
한 줄 평가 — 비용 최적화 · 경량/Stateless 에이전트 · MCP 도구 서버 호스팅의 표준 선택지
GKE
장점 (Pros)
  • 최강의 아키텍처 자유도 — Agent Gateway for GKE · Sandbox · Substrate 3대 특화 패턴
  • AI 생성 코드 격리 & 고밀도 — Agent Substrate 샌드박스(대안: Agent Sandbox) 및 1초 이내 스냅샷 복원
  • 자체 GPU/TPU 모델 통합 — Inference Gateway로 오픈 모델과 에이전트 동일 VPC 서빙
  • 기존 K8s 표준 흡수 — 사내 GitOps · 서비스 메시 · 멀티테넌시 거버넌스 그대로 적용
단점 · 고려사항 (Cons)
  • 운영·학습 곡선 가장 높음 — 멀티존·PDB·HPA·PSS·NetworkPolicy 같은 플랫폼 운영과 클러스터 수명 관리 (플랫폼 Skill 참고)
  • 초기 프로비저닝 시간 — 클러스터·서브넷·CRD 초기 프로비저닝에 상대적으로 긴 준비 시간 소요
  • 버전/모드 제약 관리 — AGW(Rapid ≥ 1.37.2), Substrate(Standard ≥ 1.37 전용) 조건 준수
한 줄 평가 — 대규모 엔터프라이즈 표준 · 코드 실행 샌드박스 · 자체 GPU LLM 환경의 최종 플랫폼
기술 상세 비교가 필요하신가요? 환경별 특화 기능과 6대 아키텍처 축 비교표는 뒤쪽 Appendix에서 바로 확인할 수 있습니다.
